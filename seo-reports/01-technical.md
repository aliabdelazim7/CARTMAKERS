# مراجعة Technical SEO وIndexability — CartMakers

**تاريخ الفحص:** 8 أكتوبر 2026  
**النطاق:** قابلية الزحف والفهرسة، استجابات HTTP، canonical، robots.txt وsitemap، prerender وJavaScript SEO، وCore Web Vitals. لا يشمل هذا التقرير استراتيجية الكلمات أو الروابط أو مراجعة المحتوى التسويقية العامة.

## الخلاصة التنفيذية

**ما تم التحقق منه:** بناء الإنتاج ينشئ 18 صفحة HTML مسبقة التوليد، وجرى جلب جميع عناوين sitemap مباشرةً باستخدام Googlebot User-Agent: كلّها أعادت HTTP 200، ولكل منها عنوان وcanonical ذاتي متوافقان في الاستجابة الأولية. ملفا robots.txt وsitemap.xml متاحان ويطابقان نطاق `www` الرسمي. الصفحة الرئيسية تعمل، والنطاق غير المزود بـwww يحوّل إلى `https://www.cart-makers.com/`، كما أن المسار لمشروع غير موجود يعيد 404 حقيقيًا.

**أعلى خلل مؤكد:** نسخ المسارات ذات الشرطة الختامية `/` لا تتصرف باستقرار بعد تشغيل JavaScript. مثلًا `/portfolio/` يعيد HTML أوليًا للـPortfolio، لكن بعد تنفيذ JavaScript في Chromium يتحول إلى الصفحة الرئيسية ويعلن canonical مختلفًا عن الاستجابة الأولية. هذا يخلق نسختين متعارضتين من عنوان واحد ومحتوى/metadata مختلفين. كما يتغير canonical في صفحة المشروع ذات الشرطة الختامية بعد تشغيل JavaScript. هذا هو إجراء الأولوية الأولى.

**مخاطرة الفهرسة التالية:** الـprerender موجود ويعمل، لكنه يضع تمهيدًا قصيرًا جدًا في HTML الأولي بدل متن الصفحة الكامل؛ وصفحة المشروع الأولية تحديدًا لا تحتوي إلا على الاسم وفقرة موجزة وروابط عامة. يستطيع Google تنفيذ JavaScript، لكن الاعتماد على مرحلة rendering اللاحقة لا يعوض HTML أوليًا مكتملًا، كما أن بعض برامج الزحف والمشاركة لا تنفذ JS.

**لا توجد بيانات كافية للجزم بأن الصفحات مفهرسة حاليًا أو أن Core Web Vitals ناجحة ميدانيًا.** استجابة 200، ووجود Sitemap، وحتى نجاح اختبار Lighthouse سابق لا تثبت الإدراج في فهرس Google أو أداء المستخدمين الفعلي.

## النتائج الموثقة (Verified)

### 1. Crawlability، indexability وحالات HTTP

- أمر `npm run build` اكتمل بنجاح محليًا، وأنتج `dist/` مع `/`, `/portfolio`, `/policies` و15 صفحة `/projects/:slug`؛ أي 18 صفحة HTML مسبقة التوليد. هذا يطابق 18 عنوانًا في sitemap.
- اختُبرت عناوين sitemap الـ18 عبر HTTPS بطلب يحمل `User-Agent: Googlebot`. **كل عنوان أعاد 200**، واحتوى الرد على `<title>` وcanonical ذاتي مطابق للمسار القياسي. والاستجابة الأولية أعادت HTML route-specific، لا shell فارغًا.
- اختُبر مسار مشروع غير موجود (`/projects/not-a-real-project`)؛ النتيجة **HTTP 404** من Vercel، وليست 200 ناعمة. واختُبر `/foo` أيضًا وأعاد 404. هذه نقطة إيجابية مهمة للمسارات المفقودة.
- جرى فتح `[robots.txt](https://www.cart-makers.com/robots.txt)` و`[sitemap.xml](https://www.cart-makers.com/sitemap.xml)` مباشرةً، بما في ذلك بطلب Googlebot. كلاهما يعيد 200؛ Content-Type هو `text/plain; charset=utf-8` للـrobots و`application/xml; charset=utf-8` للـsitemap.
- نطاق `https://cart-makers.com/` يعيد توجيهًا دائمًا إلى `https://www.cart-makers.com/` (وثّق HANDOFF رمز 308، وتأكدت وجهة التحويل في الفحص). كما أن طلبات HTTP إلى النطاقين المختبرين تنتهي على HTTPS للنطاق الرسمي. لا تُدرج النسخة غير المزودة بـwww في sitemap.
- `/api/contact` أعاد 405 عند اختباره كطلب GET؛ وهو endpoint إرسال نموذج وليس صفحة محتوى عامة. وrobots يمنع الزحف إلى `/api/`، بما يتفق مع كونه endpoint لا صفحة بحث.
- الموقع صغير: 18 URL عامة في sitemap وفق القياس الحالي. **لا توجد إشارة تقنية في عينة الفحص تستدعي معالجة crawl budget قبل استقرار URL variants والـprerender.**

### 2. خلل عالي الأولوية: الشرطة الختامية تغيّر الصفحة بعد JS

**الدليل القابل لإعادة الاختبار:**

- `GET https://www.cart-makers.com/portfolio/` يعيد 200. في HTML الأولي: عنوان أعمال CartMakers وcanonical إلى `https://www.cart-makers.com/portfolio`.
- في اختبار Chromium headless على العنوان نفسه بعد تنفيذ JavaScript: تغيّر `<title>` إلى عنوان الصفحة الرئيسية، وتحوّل H1 إلى H1 الصفحة الرئيسية، وأصبح canonical `https://www.cart-makers.com/portfolio/`.
- السبب ظاهر في `src/main.jsx`: فحص المسار في السطر 165 يطابق `/portfolio` حرفيًا، لا `/portfolio/`؛ لذلك يسقط المسار ذو الشرطة الختامية إلى fallback الصفحة الرئيسية. كما يبني `updateSeo()` canonical من `window.location.pathname` مباشرة (نحو السطر 146)، فيحوّل canonical في المسارات المنتهية بشرطة إلى نسخة أخرى.
- صفحة المشروع `/projects/velora/` تحتفظ بواجهة المشروع بعد التنفيذ، لكن canonical الأولي يشير إلى `/projects/velora` ثم يغيّره JS إلى `/projects/velora/`. هذه إشارة canonical مزدوجة لا ينبغي تركها.
- عناوين query مثل `/projects/velora?utm_source=test` تعيد محتوى المشروع وcanonical إلى النسخة النظيفة دون query في HTML الأولي؛ هذا السلوك صحيح قبل JS.

**الأثر المتوقع:** نسخة `/portfolio/` قد تُفهم على أنها نسخة/عنوان مستقل بمحتوى مختلف، أو كأن محتوى HTML الأولي لا يطابق HTML المعرّض للفهرسة بعد rendering. وفي صفحة المشروع تتضارب إشارات canonical بين المصدر الأولي وDOM المُصيّر. يضعف ذلك توحيد إشارات الزحف والفهرسة ويزيد احتمالات اختيار Google لعنوان غير المرغوب.

### 3. Prerender وJavaScript SEO

- يعرّف `package.json` البناء بأنه `vite build && node scripts/prerender.mjs`، ويشغّل `vercel.json` أمر البناء مع مجلد `dist`. اختبار البناء المحلي يؤكد إنشاء 18 صفحة.
- الملف `index.html` في المصدر يحتوي mount فارغًا (`<div id="root"></div>`). لكن سكربت البناء يملأه في ملفات `dist`؛ وهذا ما ظهر أيضًا في HTML المنشور الذي فُحص. لذلك لا يصح استنتاج أن النسخة المنشورة shell فارغ لمجرد قراءة `index.html` وحده.
- الـprerender يضع محتوى قابلًا للقراءة وروابط في HTML الأولي: الصفحة الرئيسية فيها H1 ووصف مختصر، والـPortfolio فيه روابط إلى المشاريع، وصفحة السياسة فيها مقدمة وفقرة، وصفحات المشاريع فيها اسم المشروع وفقرة وصف وروابط إلى Portfolio والتواصل.
- مع ذلك، القوالب في `scripts/prerender.mjs` (تقريبًا الأسطر 56–68) ليست نسخة محتوى كاملة للصفحات في React؛ ولا تعرض صفحات المشروع الأولية سوى ملخص، ولا تعرض عناصر المشروع المهيكلة/تفاصيل دراسة الحالة الموجودة في تعريفات التطبيق. بعد تنفيذ JS تُحمّل واجهة أغنى. هذا يجعل قيمة المحتوى التي يراها الزاحف قبل rendering محدودة، خصوصًا في صفحات المشاريع.
- `src/main.jsx` يستخدم `createRoot()`، ويعدّل title وdescription وcanonical وOG من `useEffect`. للروابط القياسية المختبرة، canonical موجود أصلًا في HTML ويتطابق مع JS؛ لا تعتمد الصفحات القياسية على إدخال canonical عبر effect وحده. لكن هذا غير صحيح لنسخ الشرطة الختامية كما في النتيجة السابقة.

### 4. Canonical، Sitemap وRobots

- عناوين sitemap مطلقة على النطاق الرسمي `https://www.cart-makers.com`، والـ18 عنوانًا جميعها أعادت 200 عند فحص Googlebot.
- XML صالح للتحليل، ويحتوي 18 عنصر `<loc>`: الصفحة الرئيسية وPortfolio والسياسات و15 مشروعًا. كل صفحة مختبرة تضع canonical ذاتيًا إلى عنوانها القياسي في HTML الأولي.
- robots الحالي يسمح عمومًا بالزحف (`Allow: /`)، ويمنع `/api/`، ويعلن عنوان sitemap الصحيح. لم يظهر حظر يمنع الصفحات العامة أو ملفات CSS/JS اللازمة.
- يحتوي sitemap على `lastmod` للصفحة الرئيسية وPortfolio والسياسات بقيمة `2026-10-08`، ولا يضع `lastmod` لباقي صفحات المشاريع. وجود القيمة موثّق؛ **لم يمكن التحقق من أن هذا التاريخ هو تاريخ تعديل المحتوى الفعلي**. لا تضف أو تجدّد `lastmod` آليًا لمجرد إعادة النشر.
- يدعم التنفيذ الحالي العربية RTL. يذكر `plan.md` مسارًا إنجليزيًا `/en`، لكن `public/manus-routes.json` لا يعلنه وطلب `/en` على الإنتاج أعاد 404. لا توجد حاجة إلى hreflang ما دامت النسخة الإنجليزية ليست مسارًا منشورًا؛ المطلوب أولًا تأكيد هل `/en` مطلب قائم أم أن الخطة قديمة.

### 5. HTTP caching، الصور والأداء التقني الظاهر

- الاستجابات المفحوصة لملفات JS/CSS وWebP أعادت 200، وظهرت ترويسة `Content-Encoding: br` لملفي JS/CSS؛ والـWebP يُقدّم بنوع محتوى `image/webp`. كما تعلن الصور المستخدمة في React أبعاد `width` و`height` و`decoding="async"`، ومعظم صور الشبكة البعيدة تستخدم lazy loading.
- ملف البناء المحلي أفاد بأحجام: JS ‏289.32 kB خام / 88.53 kB gzip، وCSS ‏37.03 kB / 7.70 kB gzip. هذا قياس build، لا قياس سرعة تحميل المستخدم أو LCP.
- في فحص الأصول المنشورة، ظهر `Cache-Control: public, max-age=0, must-revalidate` لملفات JS/CSS المسماة ببصمة build وكذلك لصورة WebP. هذا لا يستفيد من الكاش طويل المدى للأصول ذات الأسماء المبصومة؛ إذ يمكن عادةً جعل `/assets/*` المبصومة طويلة العمر و`immutable`. لا تطبق ذلك على صور عامة ذات أسماء ثابتة إلا مع استراتيجية تحديث/نسخ مناسبة.
- سبق وجود `preconnect` إلى Google Fonts في `index.html` وفق المصدر. لم يُقَس زمن استجابة الخطوط أو أثرها على LCP/CLS في هذا الفحص.

### 6. Core Web Vitals — ما تقوله الملفات فقط

- يسجل `HANDOFF.md` قياس Lighthouse سابقًا للصفحة الرئيسية بتاريخ 2026-10-08: Mobile Performance 91 وDesktop 88؛ وفي mobile: FCP ‏2.3s، LCP ‏2.3s، TBT ‏70ms، CLS ‏0.022. هذه **قيم منقولة من ملف المشروع وليست قياسًا ميدانيًا مستقلاً أجري ضمن هذا الفحص**.
- LCP ‏2.3s وCLS ‏0.022 في ذلك القياس المختبري يقعان تحت حدود “جيد” المنشورة من Google، لكن هذا لا يثبت أن حد 75th percentile ميداني متحقق. TBT ليس INP ولا يستبدل قياس INP.
- لا يتضمن HANDOFF قيمة INP أو بيانات CrUX/field، ولا يظهر ضمن المشروع إعداد Real User Monitoring. لذلك حالة INP، وCore Web Vitals الميدانية للصفحات الداخلية، وحالة المستخدمين الفعلية **Unknown**.

## Unknowns وما يلزم لإغلاقها

1. **حالة الفهرسة الحقيقية:** لا أملك وصولًا إلى Google Search Console أو Google Indexing reports ضمن هذا الفحص. لا يمكن إثبات ما إذا كانت عناوين 18 كلها مفهرسة، أو canonical المختار لدى Google، أو وجود استبعاد/Soft 404/Sitemap processing issue الآن. ورد في HANDOFF تاريخ سابق لمشكلة “Couldn't fetch” ثم اختبار نجاح مباشر؛ الرد المباشر الحالي ناجح، لكن حالة Search Console الحالية لم تُفحص.
2. **Core Web Vitals الميدانية:** لا توجد قيمة INP أو بيانات CrUX/field أو توزيع موبايل/سطح مكتب للصفحات الداخلية متاحة في الملفات. قياس Lighthouse المدرج في HANDOFF لا يجيب عن الأداء الميداني عند 75th percentile.
3. **المسار `/en`:** `plan.md` يذكره، لكن ملف المسارات الحالي لا يعلنه وProduction يعيد 404. يجب على مالك المنتج تأكيد ما إذا كان ذلك خطأ بالخطة أو صفحة لازمة.
4. **دقة `lastmod`:** ملف sitemap يضع تاريخ 2026-10-08 لثلاثة URLs؛ لا يوجد في هذا الفحص مصدر يثبت أن التغيير الجوهري لتلك الصفحات حدث في ذلك التاريخ.
